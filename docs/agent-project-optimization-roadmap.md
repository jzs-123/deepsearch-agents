> 审查日期：2026-10-13
>
> 审查范围：Agent 编排、会话历史、长期记忆、自研 RAG、FastAPI/WebSocket、React 前端、安全、可观测性、测试与部署。

> 目标：在保留当前教学价值和开发效率的前提下，把项目逐步提升为稳定、可评测、可扩展的生产级 Agent 系统。

## 1. 当前项目基线

项目目前已经具备较完整的主链路：

- 主 Agent 调度网络搜索、数据库查询和自研 RAG 三个子 Agent。
- 支持上传附件、生成 Markdown/PDF、WebSocket 实时事件和文件下载。
- 自研 RAG 已支持混合检索、重排、查询改写、低分拒答、文档版本替换、引用溯源、缓存、审计、Qdrant 后端和 RAGAS/离线评测。
- 会话历史存入 SQLite，长期记忆通过独立 SQLite Store 持久化。
- 已有请求 ID、基础鉴权开关、并发限制、健康检查和 Prometheus 文本指标。
- 后端测试数量较多，但测试重点明显集中在 RAG 模块。

因此，后续优化应优先解决“现有能力能否安全、稳定地长期运行”，而不是继续增加新的 Agent 或工具。

## 3. P0：上线前优先处理

### 3.1 会话、任务和文件必须绑定用户身份 ✅

**当前现状**

- `app/security/auth.py` 已实现 `Identity` 和 `scope_thread_id()`，但 `scope_thread_id()` 当前没有被业务代码调用。
- `/api/task` 解析了身份，但历史会话、取消任务、普通文件上传、文件列表、下载、知识库上传和 WebSocket 没有统一执行身份校验。
- `sessions` 表只有 `thread_id/title/time`，没有 `user_id` 和 `tenant_id`。
- 只要知道 `thread_id` 或输出文件路径，就可能读取、删除或取消其他会话的数据。

**建议方案**

1. 在 API 入口统一解析身份，不让各路由各自决定是否鉴权。
2. 给 `sessions` 增加 `user_id`、`tenant_id`，所有查询都带身份条件。
3. 将外部 `thread_id` 转换成内部作用域 ID，或保存独立的 owner 字段。
4. 任务、上传目录、输出目录、WebSocket 订阅和下载全部校验 owner。
5. 知识库增加 `private/tenant/shared` 作用域，避免所有用户默认看见全部知识库。

**验收标准**

- 用户 A 无法列出、读取、删除、取消、订阅或下载用户 B 的任何会话资源。
- 即使 A 猜中 B 的 `thread_id` 或文件路径，接口仍返回 403/404。
- 鉴权开启和关闭两种模式都有 API 集成测试。

**完成记录（2026-10-13）**

- 用户身份由服务端凭证绑定，拒绝通过请求头冒用用户或租户。
- 会话表自动迁移 owner 字段，列表、历史、任务、取消、上传、文件及 WebSocket 全部校验归属；删除后的 ID 不能被接管。
- 网页增加 API Key 登录，HttpOnly Cookie 同时支持 WebSocket 和下载；限制允许的页面来源。
- Agent 文件访问限定在当前会话目录，用户记忆包含租户命名空间。
- 新知识库按租户隔离，公共旧库需显式允许；修复 Pipeline 缓存和远程 Qdrant collection 的同名库串用。
- 配置及旧数据处理见 `docs/agent-security.md`。默认仍保留本地匿名模式。
- 验证：完整后端 `611 passed, 4 skipped`；另补真实框架/假模型的 Agent 沙箱运行测试 `1 passed`；前端生产构建通过。没有调用真实模型或远程 Qdrant。

### 3.2 收紧普通附件上传 ✅

**当前现状**

知识库上传已经使用 `safe_upload_name()`、格式白名单和 50 MB 限制；普通会话附件上传仍直接拼接 `thread_id` 与原始 `file.filename`，也没有文件大小限制。

**建议方案**

- 普通附件复用知识库上传的文件名清洗逻辑。
- 校验 `thread_id` 格式，禁止路径字符。
- 采用流式写入并限制单文件大小、单次文件数和会话总容量。
- 使用服务端生成的存储名，另存原始展示名。
- 只允许业务需要的后缀；生产环境增加 MIME/文件头检查和恶意文件扫描。
- 上传失败时删除未写完的临时文件。

**验收标准**

- `../`、绝对路径、重名覆盖、超大文件和不支持格式都有自动化测试。
- 任意上传内容都不能写出当前会话目录。

**完成记录（2026-10-13）**

- 新增 `app/api/uploads.py`，集中处理普通会话附件上传。
- `thread_id` 只允许字母、数字、下划线和短横线，阻断目录穿越。
- 文件名增加路径字符、Windows 保留名、控制字符、长度和后缀白名单校验。
- 限制一次最多 10 个文件、单文件 50 MB、单会话总量 200 MB。
- 采用分块读取、临时文件和原子替换；任一文件失败时回滚本批次全部文件。
- 已存在的同名文件返回 409，不再静默覆盖。
- 新增路径穿越、危险文件名、格式、超限、覆盖和批量回滚测试。
- 验证结果：`31 passed in 2.17s`。

### 3.3 将后台任务与事件改为可恢复状态 ✅（单 Worker 阶段）

**当前现状**

- `active_tasks`、并发信号量和 WebSocket 连接全部保存在单个 Python 进程内。
- 服务重启后任务状态丢失；多 Worker 部署时不同进程看不到彼此的任务。
- WebSocket 断线期间的事件不会补发；每个 `thread_id` 只保留一个连接，新标签页会替换旧连接。
- 前端只保留最近 120 个实时事件。

**建议方案**

第一阶段先使用现有 SQLite 增加 `tasks` 和 `task_events` 表，保存：

- `task_id/thread_id/owner/status/created_at/started_at/finished_at`
- 输入、最终结果、错误摘要、取消原因
- 带递增序号的事件

增加接口：

- `GET /api/tasks/{task_id}`：查询真实状态。
- `GET /api/tasks/{task_id}/events?after=<seq>`：断线补发事件。

需要多机或多 Worker 时，再把执行迁移到 Redis + Celery/Dramatiq/RQ 等持久队列。不要在单机阶段同时引入队列、事件总线和新的数据库。

**验收标准**

- 页面刷新后能恢复运行中、成功、失败或取消状态。
- WebSocket 断开后重连不会丢事件或重复事件。
- 服务重启后，未完成任务会被标为中断或重新调度，不会永久显示“运行中”。

**完成记录（2026-10-13）**

- SQLite 自动创建 `tasks/task_events`，保存独立任务 ID、owner、状态、输入、结果、错误、时间和递增事件序号。
- 新增任务快照、会话最新任务、按序补发接口；所有接口执行归属校验。
- 事件先落库再推送；服务启动将遗留运行记录标为中断，停服也区分中断与用户取消。
- 同一会话的新任务等待旧任务退出，完成回调释放并发额度，覆盖启动前取消。
- 专项状态/API/Agent 回归 `19 passed`；部署边界及接口见 `docs/task-recovery.md`。多 Worker 执行队列仍在第三阶段，不自动重跑有副作用的工具。

### 3.4 用 Schema 约束 Agent 最终输出 ✅

**当前现状**

`monitor.report_task_result()` 会把模型文本包装在固定 JSON 外壳中，但 `answer` 本身仍是自由文本。这只能保证传输包是 JSON，不能保证 Agent 结果结构稳定。

**建议方案**

定义一个最小 Pydantic 模型，例如：

```python
class AgentResult(BaseModel):
    status: Literal["success", "partial", "refused", "failed"]
    answer: str
    sources: list[SourceRef] = []
    artifacts: list[ArtifactRef] = []
    warnings: list[str] = []
```

优先使用模型提供商的 `json_schema`/structured output；如果当前兼容接口不支持，则让主 Agent 调用一个 `submit_final_result` 工具，由工具参数 Schema 强制校验。只在边界执行一次解析和有限重试，不要在多层代码中到处使用正则修复 JSON。

**验收标准**

- 最终结果 100% 通过 Pydantic 校验。
- 缺字段、类型错误、Markdown 代码块包裹 JSON 等情况都有测试。
- 前端只消费版本化结构，例如 `schema_version=2.0`，并保留旧版兼容迁移。

**完成记录（2026-10-13）**

- 主 Agent 使用 `ToolStrategy(AgentResult)`，最终答案、来源和文件通过严格 Pydantic 校验；最多两次格式纠错，并限制图执行步数。
- 任务数据库保存 `schema_version=2.0` 结果，前端兼容旧版文本和 1.0 事件；失败输出进入任务失败状态。
- 离线测试覆盖缺字段、错误类型、空答案、未知状态、Markdown 包裹、重试预算及前端版本兼容。
- 真实 DeepSeek 接口发现思考模式与强制工具调用冲突，已修复并通过前端代理和浏览器验证最小任务；复杂任务与其他真实数据源仍需独立验收。

### 3.5 建立统一任务状态机和错误语义 ✅

**当前现状**

`run_deep_agent()` 捕获普通异常后发送错误事件，但不会继续抛出；调用层无法可靠区分成功与失败。取消接口则在任务真正停止前就返回 `cancelled`。

**建议方案**

统一状态：

```text
queued -> running -> succeeded
                  -> failed
                  -> cancelling -> cancelled
                  -> interrupted
```

- 业务层记录失败后重新抛出异常，任务包装层负责落最终状态。
- 取消接口先返回 `cancelling`，确认协程结束后再写 `cancelled`。
- 错误对用户返回稳定的错误码和安全描述；详细堆栈只进入日志。
- 前端所有按钮、提示和历史恢复都依据任务状态，而不是只依赖某个 WebSocket 事件。

**验收标准**

- 模型超时、工具异常、断网、取消、进程重启都有唯一且正确的最终状态。
- 不再出现任务失败但历史中保存为空助手回答的情况。

**完成记录（2026-10-13）**

- 实现 `queued/running/cancelling/succeeded/failed/cancelled/interrupted`，禁止覆盖终态和非法转换。
- Agent 异常重新抛出；最终回答只在流完整结束和历史保存成功后发送，空回答按失败处理。
- 取消接口先返回 `cancelling`，真实退出后报告 `cancelled`；重启和停服使用 `interrupted`。
- 对外使用稳定的执行失败、超时和服务中断错误码，模型地址/凭证及详细异常不进入用户错误文本。
- 测试覆盖失败、阶段性回答后异常、空回答、超时、取消、任务替换、重启记录和启动前取消。

## 4. P1：稳定性和质量提升

### 4.1 重新整理历史对话的数据模型

**当前现状**

- 历史已经能保存真实 user/assistant 内容，修复了只恢复最后结果的问题。
- `events_json` 仍以 JSON 字符串塞进消息表，查询和迁移困难。
- SQLite 连接是模块级全局对象，写入使用线程锁；读操作和未来多 Worker 场景缺少明确边界。
- 上下文裁剪按单条消息删除，可能留下没有对应回答的半个对话轮次。
- 当前摘要模块存在，但历史装配主要依赖“保留最近 N 条 + 删除最旧消息”。

**建议方案**

- 引入 `conversation_turns` 或为消息增加 `turn_id/task_id/sequence/status`。
- 事件独立成表，不再长期存为不可查询的大 JSON 字符串。
- 历史裁剪以完整 user-assistant turn 为单位。
- 对长会话保存滚动摘要，并记录摘要覆盖到哪个 message ID。
- SQLite 阶段增加迁移脚本；多 Worker 前迁移到 PostgreSQL。

**验收标准**

- 20 轮以上对话刷新后顺序、角色、附件、事件和最终回答保持一致。
- 裁剪后不会出现只有助手回答或只有用户问题的孤立半轮。
- 数据库升级可以从旧表无损迁移。

### 4.2 给 Agent 加执行预算和失败保护

**当前现状**

模型 HTTP 客户端有超时和重试，但主 Agent 尚未形成统一的任务总时限、最大模型调用次数、最大工具调用次数、Token/费用预算和工具级熔断策略。

**建议方案**

- 每个任务设置总超时。
- 限制模型调用次数、子 Agent 调用次数和相同工具重复次数。
- 对 Tavily、数据库、LLM 分别设置超时、有限重试和熔断。
- 重试只针对瞬时错误，不重试参数错误、权限错误和确定性业务错误。
- 达到预算后返回 `partial`，附上已经完成的结论与缺失项。

**验收标准**

- 故意让工具持续失败时，任务能在预算内结束。
- 监控可以看到停止原因、调用次数、Token、耗时和估算费用。

### 4.3 把 RAG 阈值标定应用到运行配置

**当前现状**

- 评测代码已经能推荐拒答阈值。
- `fin-bge` 的实测推荐值约为 `0.6127`，但应用默认仍是 `0.2`。
- 阈值是全局配置，不同知识库、向量模型和语料分布却可能需要不同阈值。

**建议方案**

- 先把已验证知识库的运行阈值改成标定值。
- 评测命令生成 `calibration.json`，记录知识库、模型指纹、评测集版本、推荐阈值和指标。
- 查询时优先读取知识库级阈值，缺失时才使用全局默认值。
- 向量模型、切块策略或语料大幅变化时强制重新标定。
- 补充“实体偷换、时间越界、隐私字段、错误前提、提示词注入”等 hard negative。

**验收标准**

- 每个生产知识库都有版本化的正负评测集和标定记录。
- CI 显示 Hit@k、MRR、拒答准确率、faithfulness，并在跌破门槛时失败。

**进度记录（2026-10-13，仍待业务验收）**

- 已补齐 `eval --save-calibration` 与知识库级阈值读取，校验向量指纹、数据版本和检索参数；旧标定失效后允许重做。
- 阈值或策略变化会切换检索与生成缓存键，保留文本向量缓存。
- 运行时应用与失效恢复有离线测试；未对用户实际 `fin-bge` 写入标定，独立验证集和 CI 门槛仍待完成。

### 4.4 让知识库规模增长路径真正可用

**当前现状**

- NumPy 后端需要全量内存和全量点积，适合中小规模。
- Qdrant 接口已经实现，但生产部署、迁移工具、索引参数、并发压测和备份恢复尚未形成完整流程。
- BM25 在大库上仍可能加载大量 chunk。
- 知识库入库由 HTTP 请求等待完成，大文件或 OCR 会长时间占用请求。

**建议方案**

- 小于约 10 万 chunk 时继续使用现有 NumPy，避免过早增加基础设施。
- 达到阈值后切换远程 Qdrant，并把元数据过滤下推到向量库。
- 为 NumPy -> Qdrant 提供一次性迁移命令和结果对拍。
- 大库关闭本地全量 BM25，或改用 OpenSearch/Elasticsearch 的稀疏检索。
- 入库改成后台任务，前端显示解析、OCR、切块、向量化和写库进度。
- 增加批量编码、GPU/CPU 参数、索引备份和恢复说明。

**验收标准**

- 使用 1 万、10 万、100 万 chunk 做基准测试，记录 P50/P95 延迟、内存和召回质量。
- 文档入库不会阻塞 Web 服务请求线程。
- 后端切换前后，固定评测集的质量差异在预设范围内。

### 4.5 建立完整测试金字塔和 CI

**当前现状**

- 后端已有大量测试，但绝大部分集中在 `app/rag`。
- 历史/事件只有少量契约测试，缺少任务 API、权限、上传、取消、断线恢复和 Agent 状态机测试。
- 前端只有 TypeScript build，没有单元测试、组件测试、端到端测试和 lint 脚本。
- 仓库没有 `.github/workflows`。

**建议方案**

最小 CI 分为三层：

1. `pytest`：纯函数、存储、API 和 Agent 契约测试，不访问真实网络。
2. `pnpm build` + 前端单元测试：历史恢复、WebSocket reducer、引用展示。
3. 少量 E2E：启动后端，用假模型/假工具完成“提交任务 -> 事件 -> 历史 -> 文件”闭环。

真实 LLM、Tavily 和 RAGAS 评测放到手动或定时任务，避免每个提交都产生费用和不稳定结果。

**验收标准**

- 每次提交自动运行后端测试、前端构建和关键 E2E。
- P0 中的越权、上传和任务恢复场景都进入回归测试。

### 4.6 扩充可观测性

**当前现状**

已有请求 ID、thread ID、日志、基础计数器和 `/api/metrics`，但主要是进程内累计值，缺少分阶段耗时、错误分类、Token、费用和跨 Agent trace。

**建议方案**

- 给每个任务生成 `trace_id`，每个模型调用、工具调用、子 Agent 调用生成 `span_id`。
- 记录队列等待、模型、检索、重排、数据库、网络搜索和文件生成耗时。
- 记录输入/输出 Token、模型名、重试次数和估算费用。
- 指标增加成功率、拒答率、P50/P95、取消率、工具错误率和 WebSocket 重连次数。
- 生产环境接 OpenTelemetry；日志和 trace 默认不记录原始私密文档内容。

**验收标准**

- 能从一次失败的前端任务定位到具体 Agent、工具、输入摘要和错误类型。
- 能回答“最近一小时哪个步骤最慢、哪个模型费用最高、哪个知识库拒答最多”。

## 5. P2：体验与长期质量

### 5.1 长期记忆增加质量与安全控制

**当前现状**

长期记忆已支持持久化、召回、遗忘和用户命名空间，但主要依靠词面召回；模型可以主动写入内容，错误事实和提示词也可能进入后续上下文。

**建议方案**

- 只允许写入明确类型：用户偏好、稳定事实、工作约定；普通任务内容默认不长期保存。
- 增加来源、置信度、创建者、过期时间和最后验证时间。
- 写入前做去重和冲突检查，敏感字段禁止落库或先脱敏。
- 将召回记忆标记为“不可信上下文数据”，不能覆盖系统指令。
- 后续确有质量瓶颈时，再增加向量召回；当前可先保留词面检索。

**验收标准**

- 用户可以查看、修正和删除自己的记忆。
- 过期或冲突记忆不会无提示地影响最终回答。

### 5.2 统一所有信息来源的引用格式

**当前现状**

RAG 已有结构化 `rag_sources` 和前端溯源，但网络搜索、数据库结果、上传附件和最终生成报告还没有完全统一的引用对象。

**建议方案**

定义统一 `SourceRef`：

```text
source_id, type, title, uri/path/table, locator, excerpt, retrieved_at
```

- 网络来源保存 URL、标题和访问时间。
- 数据库来源保存数据源、表/视图、查询 ID 和结果快照摘要，不向前端泄漏连接信息。
- 上传附件保存文件名、页码/工作表/行范围。
- RAG 保存知识库、逻辑文档 ID、版本、页码和 chunk。
- 最终答案与生成文件使用同一套 `source_id`。

**验收标准**

- 用户点击任意重要结论，都能看到它来自哪个网页、表格、附件页或知识库片段。

### 5.3 前端使用可恢复事件流 ✅

**当前现状**

前端已有心跳、自动重连和历史加载，但重连后不补事件，运行状态主要依赖当前内存中的 WebSocket 消息；文件列表依靠轮询。

**建议方案**

- WebSocket 事件增加 `task_id` 和递增 `seq`。
- 重连时携带最后序号，服务端补发缺失事件。
- 页面初始化先查询任务快照，再建立实时连接。
- 文件生成完成时主动推送 artifact 事件，减少固定轮询。
- 把 WebSocket 消息处理提取成纯 reducer，便于测试乱序、重复和断线场景。
- 支持同一会话多个浏览器连接，而不是一个 `thread_id` 只保存一个 socket。

**验收标准**

- 任务执行中刷新页面，结果、事件和文件状态可以完整恢复。
- 重复事件不会导致重复消息或重复文件。

**完成记录（2026-10-13）**

- 页面通过任务快照恢复真实状态，通过持久化事件接口补齐断线窗口。
- 按 `task_id/seq` 过滤旧任务、排序与去重，终态不会被历史运行事件覆盖。
- 支持同一会话多个 WebSocket，刷新后的最后一轮恢复执行过程与答案。
- 增加无额外依赖的前端测试命令 `npm test`，事件乱序、重复、旧任务过滤及终态测试 `3 passed`；生产构建通过。
- 已用临时数据库及假模型完成浏览器“提交 -> 执行中刷新 -> 事件恢复 -> 最终回答”验证。文件轮询保留，产物主动推送尚未实现。

### 5.4 规范依赖、运行数据与部署

**当前现状**

- Python 同时维护 `pyproject.toml`、`requirements.txt` 和 `uv.lock`，存在依赖漂移风险。
- 多个核心依赖只设置宽松下限，未来升级可能直接破坏兼容性。
- `app/sessions.db`、`app/data/memory.db` 和示例向量库数据已经被 Git 跟踪，运行后容易产生脏工作区，也可能误提交真实用户数据。
- 只有 MySQL Compose，没有后端/前端 Dockerfile、完整 Compose 和 CI 部署流程。

**建议方案**

- 以 `pyproject.toml + uv.lock` 为唯一依赖真源；`requirements.txt` 自动导出或删除。
- 对 Agent 框架、LangChain/LangGraph、FastAPI 等关键依赖设置兼容范围并使用自动更新 PR。
- 数据库、上传文件、输出文件、审计日志和本地知识库改放到可配置的数据目录。
- 将运行数据库从 Git 索引移除，仓库只保留 schema/migration 和最小演示数据。
- 增加后端、前端 Dockerfile，以及包含 API、前端、MySQL、Qdrant 的可选 Compose profile。

**验收标准**

- 全新机器执行文档中的单一路径即可完成安装、测试和启动。
- 正常运行项目后 `git status` 不会因数据库或缓存发生变化。

## 6. P3：随业务修改逐步整理

### 6.1 拆分超大模块，但不要单独发起“大重构”

目前较大的文件包括：

- `app/rag/pipeline.py`：约 1,200 行。
- `frontend/src/styles.css`：约 1,800 行。
- `frontend/src/workbench.css`：约 1,100 行。
- `app/api/server.py`：约 490 行。
- `frontend/src/components/ConversationThread.tsx`：约 490 行。
- `frontend/src/hooks/useDeepAgentSession.ts`：约 415 行。

建议只在修改相关功能时顺手按职责拆分：

- API 拆成 `tasks/sessions/files/knowledge_bases/health` 路由。
- 前端 session hook 拆成任务、WebSocket、历史、文件四类状态逻辑。
- CSS 按页面或组件分文件，共享 token 保持集中。
- RAG pipeline 保留统一门面，将入库、查询、生成协调逻辑分别下沉。

不要为了减少行数而一次性重写这些文件；每次拆分必须保持行为不变并由现有测试保护。
