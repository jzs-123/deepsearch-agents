# 自研 RAG 系统：从 RAGFlow 迁移到自建检索增强链路

> 版本：企业级能力批次（MVP 之上新增 OCR / 查询改写 / 元数据过滤 / 缓存 / 审计 / RAGAS 评测）

> 文档目的：说明为什么自研、怎么实现、踩了哪些坑、还有哪些没解决
> 专题文档：`rag-ocr.md`、`rag-query-rewrite.md`、`rag-enterprise-features.md`、`rag-eval-guide.md`、`rag-testing-guide.md`、`rag-upload-and-ask-guide.md`

## 一、背景与目标

### 1.1 改造前

项目原有的私有知识库能力全部外包给外部 **RAGFlow** 服务：

```
主智能体 → knowledge_base_agent → get_assistant_list()  # 查有哪些助手
                                → create_ask_delete()    # 创建临时会话 → 提问 → 删会话
                                        ↓ HTTP
                                 外部 RAGFlow 服务（独立部署）
```

这套方案能跑通，但有四个现实问题：

| 问题 | 具体表现 |
| --- | --- |
| 不可控 | 切片、召回、重排、Prompt 全在黑盒里，检索质量差时无从下手 |
| 不可调试 | 只能看到最终答案，看不到召回了什么、为什么召回、分数多少 |
| 强外部依赖 | 必须部署 RAGFlow（Docker + MySQL + ES + MinIO + Redis），环境一挂整条链路不可用 |
| 不可二次开发 | 想加混合检索、重排、引用溯源，只能改上游或绕开它 |

### 1.2 改造后

自建一条完整可控的链路，**零外部服务依赖**：

```
主智能体 → knowledge_base_agent → list_knowledge_bases()    # 有哪些库、多少片段
                                → search_knowledge_base()   # 混合检索，返回原文+分数
                                → ask_knowledge_base()      # 检索+生成，返回带引用答案
                                        ↓ 进程内调用
                app/rag 自研流水线（解析 → 切块 → 向量化 → 存储 → 混合检索 → 重排 → 生成）
```

### 1.3 功能边界

**已实现**：

- 多格式文档解析：`.pdf` / `.docx` / `.md` / `.txt` / `.csv` / 图片（`.png`/`.jpg`/`.jpeg`/`.bmp`/`.webp`/`.tif`/`.tiff`）
- **OCR**：扫描件 PDF 页转图识别、图片直接识别（Windows 内置引擎，零依赖；可插拔 rapidocr/tesseract）
- 结构感知切块（标题识别 + 段落/句子/硬切三级降级 + 重叠窗口 + 标题路径）
- 向量化：本地 BGE 中文模型 / OpenAI 兼容接口 / 离线 hash 兜底（三选一，自动降级）
- 向量库持久化（numpy 全量精确检索，装了 faiss 自动加速）+ 向量指纹校验
- 中文 BM25 稀疏检索（jieba 分词 + 倒排索引）
- 混合检索：稠密 + 稀疏 **RRF 融合**
- 重排：词面重排 / 大模型列表式重排 / 关闭（三选一）
- **查询改写**：本地规则（口语归一化 + 同义词扩展 + 专有名词强化）+ 大模型变体，多查询 RRF 融合 + 低分自动重试
- **元数据过滤**：文件级 + Markdown YAML frontmatter 自动抽取，召回后白名单过滤（等值/列表/AND）
- **缓存**：embedding / 查询结果 / 生成结果三级，键含向量指纹 + 数据版本号（默认关闭）
- **审计日志**：JSONL 追加写，含 query/filter/改写/缓存/重试/结果摘要（不含原文），可读回
- 生成：强制引用、强制只用资料、检索无依据直接拒答
- CLI：`list` / `create` / `ingest` / `search` / `ask` / `eval` / `stats` / `reset` / `audit`
- 检索质量评测（Hit@k / MRR / Recall@k / 拒答准确率）+ **RAGAS 生成质量评测**（脚本 + 零依赖离线替代）
- 离线自测脚本 + pytest 测试套件（**516 用例**）

**未实现**（下一步候选）：权限/租户隔离、BM25 增量索引、上下文压缩、表格结构化检索、真实 BGE 语义向量的持续阈值重标定。十万级 ANN 已可通过 Qdrant 后端启用。

## 二、架构与数据流

### 2.1 模块分层

```
app/rag/
├── types.py        数据模型：Chunk / RetrievedChunk / Answer
├── config.py       配置装配与校验（从 Settings 映射，可覆写）
├── loaders.py      文档解析：多格式 → 带结构信息的纯文本；图片/扫描件走 OCR
├── ocr.py          OCR：Windows 内置 / RapidOcr / None 三后端，可插拔
├── render.py       PDF 页渲染（Windows.Data.Pdf），与 OCR 解耦
├── _powershell.py  WinRT 调用层（渲染与 OCR 共用，-EncodedCommand + 文件兜底）
├── chunking.py     切块：结构优先 + 长度兜底 + 重叠
├── embedding.py    向量化：local / openai / hash 三后端
├── vectorstore.py  向量库：持久化 + 余弦检索 + 指纹校验（numpy 后端，默认）
├── qdrant_store.py 向量库：Qdrant 后端（本地嵌入 / 远程 server，可插拔，与 VectorStore 同接口）
├── bm25.py         稀疏检索：jieba 分词 + BM25 倒排索引
├── hybrid.py       混合检索：RRF 融合
├── rerank.py       重排：词面 / 大模型列表式
├── rewrite.py      查询改写：本地规则 + 大模型变体
├── metadata.py     元数据：文件级 + frontmatter 抽取 + 过滤匹配
├── cache.py        缓存：embedding / 查询 / 生成三级
├── audit.py        审计：JSONL 追加写 + 读回
├── generator.py    生成：上下文拼装 + 引用 + 拒答
├── pipeline.py     编排：ingest / search / query（改写、过滤、缓存、审计都在这里串）
├── eval.py         检索评测：Hit@k / MRR / Recall@k / 拒答率
├── eval_ragas.py   RAGAS 生成质量评测（组装层）
├── eval_offline.py 零依赖离线近似评测
├── vendor.py       pip 不可用时的 vendor/ 依赖兜底
├── cli.py          命令行入口
└── selftest.py     离线自测（不依赖大模型与向量模型）
```

### 2.2 入库链路

```
文件
 → loaders.load_document()      按后缀分派 loader，归一化文本，记录标题/页码
 → chunking.chunk_document()    标题切段 → 段落 → 句子 → 硬切；加重叠；带 heading
 → embedding.encode()           批量向量化（一次 encode 整批，不逐条）
 → vectorstore.add()            chunk_id 幂等去重 + doc_id 整篇替换
 → 落盘 chunks.jsonl / vectors.npy / meta.json
```

### 2.3 检索链路

```
问题
 ├─ 查询改写：本地规则 + 大模型变体（原始查询永远排第一）
 ├─ 查询缓存：命中则直接返回（标注 cached=True）
 ├─ 稠密路：embed(query) → 向量库余弦 Top-K
 ├─ 稀疏路：jieba 分词 → BM25 Top-K
 ├─ RRF 融合：score = Σ w_c / (k + rank_c)，k=60，w_dense=1.0，w_sparse=0.8
 ├─ 元数据过滤：召回后、重排前做白名单过滤
 ├─ 重排：Top-K → Top-N（词面重排 / 大模型列表式）
 └─ 低分重试：判定分（向量余弦）低于阈值 → 用改写变体重试
 → 生成：拼上下文（带 [编号]）→ 大模型 → 答案 + 引用
 → 拒答门槛：向量余弦 < min_score 直接拒答，不进入生成
 → 审计：整条链路写一条 JSONL（不含原文）
```

## 三、快速上手

```bash
# 1) 建库并入库（支持目录递归；PDF 需要 pypdf，缺失会给出明确提示）
python -m app.rag.cli ingest -k default -p docs/knowledge_base

# 2) 看库状态
python -m app.rag.cli stats -k default

# 3) 只做检索（不调用大模型，调参用，快且免费）
python -m app.rag.cli search -k default -q "风控策略有哪些要求" -n 5

# 4) 检索 + 生成带引用的答案
python -m app.rag.cli ask -k default -q "风控策略有哪些要求"

# 5) 评测检索质量（-n 指定 top-k，--no-rerank 可开关重排做 A/B）
python -m app.rag.cli eval -k default -e examples/rag_eval_set.json -n 5

# 6) 元数据过滤（文档头写 YAML frontmatter，如 部门/类型/密级）
python -m app.rag.cli search -k default -q "授信额度" --filter '{"部门":"风控"}'

# 7) 审计日志读回
python -m app.rag.cli audit -k default --tail 20

# 8) 离线自测（不需要大模型和向量模型，验证整条链路）
python -m app.rag.selftest

# 9) 单元测试套件（516 用例）
$env:PYTHONPATH='.uv-cache/pytest-deps'; python -m pytest tests -q
```

关键配置（`.env`，全部有安全默认值）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `RAG_DATA_DIR` | `rag_data` | 知识库数据根目录，每个子目录是一个知识库 |
| `RAG_EMBEDDING_PROVIDER` | `local` | `local` / `openai` / `hash`；本地模型不可用会自动降级到 hash |
| `RAG_EMBEDDING_MODEL` | `BAAI/bge-small-zh-v1.5` | 中文效果与体积平衡最好的一档 |

## 四、核心设计取舍

### 4.1 为什么自己实现 BM25 而不装 `rank_bm25`

`rank_bm25` 只接受英文空格分词，中文必须自己先分词；而中文分词恰好是这个项目最需要控制的地方（型号 `A13`、编号 `3.2.1` 必须整体保留，停用词表要自定义）。自己实现约 120 行，换来的是分词策略、IDF 平滑、`explain()` 可解释性全部可控。

### 4.2 为什么向量库用 numpy 全量点积，不用 FAISS / 向量数据库

- 万级片段下，一次矩阵乘法是毫秒级，而且**结果精确**（没有 ANN 召回损失）；
- 少一个二进制依赖，Windows 上装 FAISS 的成本高于收益；
- 全量精确检索可以当作将来引入 ANN 索引时的「正确性基准」。
- 代码已做兼容：环境里存在 `faiss-cpu` 时自动切换 `IndexFlatIP`（`vectorstore._build_index`），对外行为不变。

代价与边界写在第 6 节：数据量到十万级以上必须换索引。

### 4.3 为什么用 RRF 融合而不是分数加权求和

稠密相似度在 `[-1, 1]`，BM25 是无上界的正数，**量纲完全不同**：

- 直接相加 → BM25 分值尺度单方面决定排序，含高频词的片段会碾压语义最相关的片段；
- 先归一化再加权 → 归一化依赖当次候选集的最大/最小值，同一问题在不同知识库上权重含义会漂移，调参结果无法迁移；
- RRF 只用**名次**不用分数，天然免量纲，对单路异常高分不敏感。工业界默认做法，这里沿用。

### 4.4 重排为什么必须做，又为什么要做「不一样的重排」

BM25 已经用过词频了，如果词面重排再用一遍词频/覆盖，就是**重复排序**，几乎没有增量。所以本地重排器刻意只用 BM25 没建模的信号：查询特征词覆盖率、完整短语是否出现、命中位置是否靠前、命中密度。

另外提供 `llm` 模式：一次调用对全部候选做列表式（listwise）重排，对「语义相关但无字面重叠」的候选更敏感。代价是慢且有成本，适合离线评测或对精度要求高的场景。

### 4.5 为什么必须有 hash 离线兜底

本地向量模型需要：装 `sentence-transformers`（会牵动 torch）、联网下载约 95MB 模型、磁盘空间。任何一条不满足，整条 RAG 链路就完全不可用。

`hash` 后端用字符 n-gram 哈希 + sublinear TF + L2 归一化，**没有真正的语义能力**，但能让「解析 → 切块 → 入库 → 检索 → 生成」全链路跑通，也让单元测试和 CI 不依赖网络与模型。这是工程可用性的兜底，不是质量方案，代码里已明确标注。

### 4.6 为什么 OCR 用 Windows 内置引擎，而不是 RapidOCR/PaddleOCR

本机 pip 装 torch 系依赖会空转卡死、系统 site-packages 不可写——RapidOCR（onnxruntime）、PaddleOCR（paddle）都装不上。而 Windows 自带的 `Windows.Media.Ocr` 引擎**已装简体中文包**、`Windows.Data.Pdf` 能渲染 PDF 页，整条「扫描件 → 页转图 → OCR」链路**零 pip 依赖**就能跑通。

代价是质量与平台绑定：正文页识别好、设计类封面页差（丢数字、错字随倍率变），且只在 Windows 可用。因此把它做成**可插拔后端**（`windows` / `rapidocr` / `none`），并定位为**兜底**而非常规路径——有文本层的 PDF 绝不触发 OCR（见 5.14）。详见 `docs/rag-ocr.md`。

### 4.7 为什么查询/生成缓存默认关闭

查询缓存一旦陈旧就是「返回过期答案」，这种风险不该由默认配置承担。所以三级缓存（embedding / 查询 / 生成）统一受一个总开关控制，**默认 false**。embedding 缓存虽然是内容寻址（同文本+同后端=同向量，语义上不可能陈旧），也一起关，保持「一个开关解释全部行为」。缓存键里都带**向量指纹 + 数据版本号**，库内任何 chunk 增删改都会让查询/生成缓存整体失效。

### 4.8 为什么审计日志"绝不拖垮查询"

审计是旁路关注点，不该影响主链路。所以：JSONL 追加写、**不含原文**（避免日志爆炸）、写失败只 warning 不抛异常。这样即使审计目录不可写，检索/问答也照常返回——审计是「尽力而为」的记录，不是「必须成功」的依赖。

### 4.9 为什么低分重试的判定分必须用向量余弦

查询改写会带来多个变体，每个变体各有检索结果。判断"要不要用变体重试"、以及"重试后是否改善"，必须用**同一个尺度**。重排分（词面覆盖率/大模型打分）随重排模式变、绝对尺度不稳定；向量余弦是唯一跨模式稳定的量。所以重试判定与最终拒答统一用 `grounded_score()`（向量余弦），排序才用重排分。这是 5.10 那类"排序分/判定分混用"教训在改写链路里的再次应用。

## 五、技术难点与遇到的问题（核心章节）

以下每一条都是本项目实际踩到的，按「现象 → 原因 → 解决 → 遗留」记录。

### 5.1 PDF 解析：排版信息在纯文本里丢失

**现象**：抽取出来的 PDF 文本错行、页眉页脚混入正文、表格变成一串数字、某些页完全空白。

**原因**：pypdf 只能按内容流顺序取文本，拿不到版面坐标；扫描件根本没有文本层。

**解决**：

- 逐页抽取，并给每页打上「第 N 页」伪标题，引用时能定位到页码；
- 识别出未提取到文本的页并计入 `warnings`，而不是静默产出空文档；
- 文本归一化：统一换行、去 `\xa0`/零宽字符、**去掉中文字符之间被逐字抽取产生的空格**、压缩连续空行；
- 单页解析异常不中断整篇（逐页 try/except）。

**遗留**：没有 OCR，扫描件仍不可用；双栏排版的阅读顺序仍可能错乱；表格只能线性读取，跨页表头会丢。彻底解决需要引入版面分析模型（如 PP-Structure）或 PDF 转 Markdown 工具。

### 5.2 切块：固定字数切分会同时破坏语义与结构

**现象**：按固定 500 字切分后，答案被切在句子中间；标题和它的正文被分到两个 chunk；表格被切散。

**解决**：四级降级的结构感知切块：

1. 按 Markdown / 中文编号标题切大段（先识别 `#`，再识别「第三章」「一、」「3.2.1」）；
2. 段内按空行切段落；
3. 段落超长按中文句末标点（`。！？；`）切句；
4. 单句仍超长（无标点长表格行）才硬切。

再叠加两个优化：chunk 头尾重叠（默认 80 字，按句边界回退，不从句子中间截断），以及每个 chunk 带 `heading` 标题路径，让「第三章 > 3.2 风控」这类结构信息也参与检索匹配。

**踩坑细节**：中文编号标题没有 `#` 标记，正文里的编号列表（`1. 先做 A，再做 B。`）也匹配编号正则。最初把正文句子粘进了标题，出现 `一、核心结论金融与电商业务正在加速融合……` 这种畸形标题。解决是加了一个判定：编号后的内容**短且不含标点**才算标题，否则当正文。

**遗留**：`chunk_size` 没有自动化调优，目前是手工用评测集对比（500 是基于示例语料的经验值，中文技术文档常用 400~600）。

### 5.3 `re.MULTILINE` 缺失导致标题识别静默失效

**现象**：单元级调试里 `_MD_HEADING.match("# 标题")` 返回 True，但整篇文本 `finditer` 一条都匹配不到，结果是整篇文档只切出 1 个 chunk、`heading` 全为空。

**原因**：`re.compile(r"^(#{1,6})...")` **漏了 `re.MULTILINE`**。没有它时 `^` 只匹配整串开头、`$` 只匹配整串末尾；逐行 `match()` 看起来一切正常（因为每次只传了一行），全文 `finditer` 则完全失效。

**教训**：这类 bug 不会抛异常，只会让效果变差，最难发现。判据是看 `compiled.flags` 里有没有 8（`re.MULTILINE`）。已修复并在代码里加了注释说明。

### 5.4 中文分词歧义导致重排完全失效

**现象**：查询「风控模型的准确率是多少」，文档里写的是「准确率为 91.5%」，重排后**名次一点没变**，调试发现所有候选的重排分都是 0。

**原因**：jieba 把查询切成「准确/率」，而文档里是「准确率为」——按 token 做子串匹配，一个都命中不了，覆盖率 0、位置分 0，全为 0 的分数排序等于没重排。

**解决（两级兜底）**：

1. 特征词除分词 token 外，额外加入**中文相邻二元组**（「准确」「确率」「率是」…），绕开分词结果的分歧；
2. 再加一路**字符级覆盖率**（去掉「的了吗呢」等无区分度单字），即使分词完全不同，字符大面积重合也说明相关。

**遗留**：词面重排本质上无法处理「同义不同词」（如「转化率」vs「成交比例」），这类只能靠向量召回或 `llm` 重排补。

### 5.5 换向量模型会静默产生垃圾结果

**现象**：用模型 A 入库、用模型 B 查询，检索不报错，但结果毫无相关性。

**原因**：不同模型的向量空间不可比，跨空间算余弦相似度在数学上毫无意义；而代码层面维度可能恰好相同，不会触发任何异常。这是 RAG 里最阴的一类 bug。

**解决**：`meta.json` 记录向量后端指纹（`后端:模型:维度`），`VectorStore.open()` 时校验：

- 指纹不一致且库非空 → 抛 `EmbeddingMismatchError`，错误信息里直接给出重入库命令；
- 追加写入时维度不一致 → 同样报错；
- `chunks.jsonl` 与 `vectors.npy` 行数不一致（落盘撕裂）→ 按较小长度截断并告警。

**代价**：换模型必须整库重跑。这是**正确性优先**的必然代价，不做「自动迁移」。

### 5.6 默认数据目录踩到 Windows 权限/沙箱限制

**现象**：`app/data/rag` 建不出来，报 `PermissionError: [WinError 5]`，但同目录写文件是正常的。

**排查过程**：ACL 看起来授予了写权限（`Authenticated Users:(M)`），修复 ACL 后**依然失败**；进一步二分测试发现：工作区根目录 `output/` 下可以建目录，而 `app/`、`docs/` 下不行——说明限制是按目录生效的，不是所有者或 ACL 缺失问题。

**解决**：把知识库数据根目录从 `app/data/rag` 移到项目根独立的 `rag_data/`。这个改动本身也更好：**数据与代码分离**，备份/迁移/清理缓存时不会误删数据。

**遗留**：这是宿主环境限制，不是代码缺陷；换机器若默认路径不可写，用 `RAG_DATA_DIR` 覆盖即可（`VectorStore.open` 用 `mkdir(parents=True)`，正常情况下会自动创建多级目录）。

### 5.7 重复入库导致「检索结果全是同一段话」

**现象**：同一份文档入库两次后，检索结果里同一个片段出现多条，把其他内容挤掉。

**原因**：每次入库都无条件追加，没有去重。

**解决**：两层幂等：

- `chunk_id` = `sha1(来源路径 | 序号 | 内容前 120 字)`，`VectorStore.add()` 遇到已存在的 `chunk_id` 直接跳过；
- `doc_id` = 整篇正文指纹，入库前先 `delete_document(doc_id)` 做**整篇替换**——文档更新后旧内容不会残留在库里（这点比单纯去重更重要，否则会检索到过期版本）。

**踩坑**：`add_texts()` 最初没走 `chunk_document`，而是「一段文本 = 一个 chunk」，导致长文入库后只有一条 3000 字的 chunk，检索要么全中要么全漏。已改为与文件入库共用同一条切块路径。

### 5.8 PDF 依赖缺失被静默跳过

**现象**：入库报告 `files_indexed: 0`，但看不出为什么。

**原因**：`load_pdf` 里 `import pypdf` 失败被上层 catch 成「跳过该文件」，只留了一行 warning。

**解决**：loader 抛出的错误信息里带上可执行命令（`缺少 pypdf 依赖,请执行: pip install pypdf`），并把每个跳过原因写进 `IngestReport.warnings`，CLI 默认打印出来。

**教训**：入库这种批量操作，「跳过了什么、为什么跳过」必须比「成功了多少」更显眼。

**额外发现（依赖安装本身也会卡）**：本次开发环境里 `pip install` 两次卡死——进程空转、CPU 占用持续上升、却没有任何网络连接（`Get-NetTCPConnection` 为空），而 `urllib` 直连 PyPI 完全正常。同时系统 site-packages 目录对该进程不可写。为了不阻塞验证，最后采用的方式是：直接下载纯 Python wheel 并解压到项目根的 `vendor/` 目录，由 `app/rag/vendor.py` 在导入失败时惰性加入 `sys.path`。

这是一个**逃生通道**而不是推荐做法：正常环境请用 `pip` / `uv` 安装。它的价值在于让「依赖装不上」不再等于「整条链路不可用」——`vendor/` 里放的是纯 Python 包（如 pypdf），不含任何编译产物。

### 5.9 中文脚本与输出被 PowerShell 管道编码破坏

**现象**：同一段脚本，直接跑正常，管道给 `Select-Object` 后报各种诡异的 `SyntaxError`（内容里的中文变成乱码）。

**原因**：Windows 上 PowerShell 与子进程之间的管道编码不是 UTF-8，Python 源码和 stdout 都会被破坏。

**解决**：验证脚本全部改为「**输出重定向到 UTF-8 文件，再读文件**」，并设置 `PYTHONIOENCODING=utf-8`。

**教训**：在 Windows 上做中文数据处理，「测试结果本身的编码」也要当成被测对象，否则会浪费大量时间在假故障上（本项目在这上面真实浪费过时间）。

### 5.10 词面重排的分数尺度污染了拒答阈值

**现象**：同一份数据、同一个 `min_score=0.2`，关闭重排时拒答准确率 100%，开启词面重排后掉到 **50%**——一个无关问题（「公司食堂本周的菜单」）本来最高分 0.1722 会被正确拒答，重排后变成 **0.2172**，越过阈值，于是系统开始拿无关片段去生成答案。

**原因**：`min_score` 一直是拿「向量余弦」标定的，但重排后 `item.score` 变成了**重排分**（词面覆盖率加权）。词面覆盖率的取值范围与实际分布跟余弦完全不同，同一个阈值在两种模式下含义不同。**把排序分和判定分混用，是这个 bug 的根源。**

**解决**：把「排序」和「判定」两个职责分开：

- 排序：用重排分（这是重排的意义所在）；
- 判定：统一用**向量余弦**（`pipeline.grounded_score()`，取候选里第一条有 `dense_score` 的分数）。

修复后同样数据、同样阈值：`Hit@5 100% / MRR 0.9167 / 拒答 100%`，两类分数分层清晰。

**教训**：任何「阈值」都必须写清楚它比较的是**哪个量**。多路融合 + 重排之后,分数空间已经换了三套，用错一套不会报错，只会悄悄降低准确性。

### 5.11 评测脚本自身的两个 bug（假失败与假通过）

第一次跑评测得到 `Hit@5 = 0.00%`，但逐条看检索结果**完全正确**。

- **假失败**：入库时 `source_path` 是相对路径（`sub_dir/报告.md`），评测集里只写了文件名（`报告.md`），用 `==` 比对永远不相等。修正为按文件名归一化比对（忽略目录与大小写）。
- **假通过**：拒答判定用的是排序分，与线上真实判定不一致，属于「评测通过了但线上行为不一样」。修正为与线上共用 `grounded_score()`。

**教训**：评测脚本是「尺子」，尺子本身必须先校准。用错比对逻辑会得出 0% 这种极端结论，很容易让人误以为检索算法有问题。

### 5.12 生成层的幻觉与拒答

**风险**：检索到无关片段时，大模型倾向用参数化知识「补全」一个看起来很专业的答案。

**三层约束**：

1. **提示词铁律**：只用【参考资料】作答、每条结论标 `[编号]`、资料不足必须回答「知识库中没有找到相关信息」、数字/金额/比例/日期必须与原文完全一致；
2. **入口拒答**：`grounded_score() < min_score` 直接返回拒答文案，**不进入大模型**（省钱且最可靠）；
3. **出口识别**：模型输出里出现「没有相关信息/无法回答/资料中没有」等标识且回答较短，标记 `grounded=False`，评测据此统计拒答率。

**降级**：没有配置大模型或调用失败时，返回「检索到的依据 + 明确提示」而不是抛异常——检索能力独立于大模型可用。

**遗留**：拒答阈值需要按语料标定（本项目示例语料上，可答问题 0.23~0.43、不可答 0.06~0.08，0.2 落在中间；换语料必须用 `eval` 重新标定）。提示词约束不是 100% 可靠，仍可能出现「引用存在但结论超出资料」的情况。

### 5.13 性能与规模边界

| 环节 | 当前实现 | 复杂度 | 边界 |
| --- | --- | --- | --- |
| 向量检索 | numpy 全量点积 | O(N·d) | 万级片段毫秒级；十万级需换 ANN |
| BM25 | 内存倒排索引 | 查询 O(命中词的文章数) | 索引每次数据变更后整库重建；可用 `RAG_SPARSE_ENABLED=false` 关闭 |
| 向量化 | 批量 encode | 入库时一次 | 首次加载模型约数秒~十几秒 |
| 生成 | 大模型调用 | — | 实测示例问题约 20s（deepseek 推理） |

十万级以上建议切换远程 Qdrant，并设置 `RAG_SPARSE_ENABLED=false`，否则 BM25 首次查询仍会读取全库 chunk。重复查询可开启 `RAG_CACHE_ENABLED=true`；知识库数据版本变化后缓存自动失效。入库是单进程同步的，大目录仍会等待较久，增量 BM25 和后台任务留到下一版。

### 5.14 OCR 的"文本层优先"与质量边界

**现象**：同一份 PDF，有文本层的页抽取又快又准，扫描页只能 OCR，而 OCR 对设计类排版会丢数字、出错字（实测封面页 `2026年全球`→`6 年全球`，`贝莱德`→`贝菜德`）。

**教训**：OCR 是**兜底**，绝不能用它替换本来干净的文本层——否则等于用更差的结果换掉好结果。实现上必须**逐页判定**：文本层不足（默认 < 50 字符）才对该页 OCR，并用计数器取证（真实 17 页 PDF 入库 `OCR_CALLS=0`）。质量数据要如实记录差案例，不能只报好结果。

**平台坑**：Windows OCR 有稳定副作用——汉字间插空格（`风 控`）、`。`→`·`、`%`→`％`、范围号 `–`→`一`；这些空格可由 `normalize_text` 清理（注意只清 `[ \t]+`、不吞换行，见 5.18），但字符混淆无法自动修正，只能如实告知使用者。

### 5.15 查询缓存键漏掉 `top_n` 导致"少拿结果"

**现象**：开启缓存后，`top_n=2` 写入的缓存会被 `top_n=10` 的调用命中，导致只拿到 2 条结果。

**原因**：缓存键只拼了 `(query, filter, 指纹, 数据版本号)`，没包含"取多少条"这个维度。

**解决**：把 `top_n` 加进缓存键。`top_k` / `rerank` 开关仍未进键（默认缓存关闭，实际影响小），文档 §4.5 如实标注了这条局限。

**教训**：缓存键必须覆盖**所有影响结果形态的入参**。漏一个维度，缓存就从"加速器"变成"正确性 bug"，而且只在开着缓存时偶发，极难排查。

### 5.16 审计字段 `llm.called` 的语义陷阱

**现象**：拒答场景下，审计日志仍记 `llm.called=true`。

**原因**：早期实现用「客户端是否可用」当 `llm.called`，而拒答路径虽然客户端可用，却根本没发起生成调用。

**解决**：改为由 `generate()` 在真正调用 `client.complete()` 前置 debug 标记，pipeline 读这个标记——无客户端/拒答/异常都记 false。

**教训**：审计字段要记录"**实际发生了什么**"，而不是"是否具备发生的能力"。这两个量在正常路径上相同，只在降级/拒答路径上分道扬镳，而后者正是审计最该看清的地方。

### 5.17 沙箱下 3.12+ 的 `0o700` 目录自毁

**现象**：pytest 的 tmpdir 插件、`tempfile.mkdtemp()` 在 Python 3.12/3.13 下建出的目录，**连创建它的进程自己都访问不了**（WinError 5），目录永久不可删。

**原因**：这些 API 用 `os.mkdir(d, 0o700)` 建目录，而本沙箱对 0o700 目录有特殊的权限处理；3.10 免疫，项目自身代码（默认 mode 的 `mkdir`）不受影响。

**解决**：测试套件统一 `-p no:tmpdir`（禁用 pytest tmpdir 插件），`tmp_path` 由 conftest 用默认 mode 自供。这从设计上消掉了整类问题，而非靠 basetemp 技巧绕过。详见 `docs/rag-agent-env.md`。

### 5.18 `normalize_text` 吞掉中文之间的换行（标题吞正文）

**现象**：`# 风控报告\n\n风控模型的准确率为 91.5%。\n\n## 授信\n\n授信要求复核。` 归一化后变成 `# 风控报告风控模型的准确率为 91.5%。...`——标题把正文吞了，最终**整篇退化成 1 个 chunk、heading 全空**。

**原因**：`normalize_text` 原本用 `r"(?<=[CJK])\s+(?=[CJK])"` 删中文之间的多余空格（本意是清理 PDF 逐字抽取产生的空格），但 `\s` **包含换行**，把中文之间的空行也一并删了。

**为什么难发现**：段落以标点结尾时不触发（`第一段。\n\n第二段。` 保持不变），只有「标题行以汉字结尾 + 下段以汉字开头」时才触发；症状与 5.3（漏 `re.MULTILINE`）**一模一样**——都是标题识别失效、整篇 1 个 chunk，但根因完全不同，排查时极易误判。

**解决**：改用 `r"(?<=[CJK])[ \t]+(?=[CJK])"`，只清空格与制表符、保留换行。修复后重建示例库：chunk 数 238 → 248（恢复了 10 处被错误合并的结构边界），评测指标无回退。

### 5.19 文本层"有字但是乱码"：长度规则覆盖不到的坏文本层

**现象**：一份简历制作工具导出的 PDF 入库后检索全是乱码（藏文/缅甸文/拉丁扩展区字符混合，`Ġ`、`ğ` 之类），dense 通道以 0.3575 召回并**越过拒答阈值 0.2**，乱码被送进大模型，回答不出来。BM25 完全不命中（`sparse=None`），词面重排分为 0。

**原因**：这类 PDF 的内嵌字体是子集字体且**没有 ToUnicode CMap**（超级简历/Canva/稿定等导出器的通病），pypdf 拿不到"字形→文字"的映射，只能把原始 CID 直接当 Unicode 输出——空格变成 `Ġ`（0x20+0x100），汉字变成随机藏文/缅甸文。关键在于：**乱码页的字符数并不少**，`min_text_chars` 长度规则完全覆盖不到；5.14 的"文本层优先"防住了"该 OCR 没 OCR"，防不住"文本层存在但是垃圾"。

**解决**：`load_pdf` 增加文本层**质量检测**（`mojibake_ratio()`，白名单法）：

- 统计落在「ASCII 可见字符 + CJK 统一表意 + 中文标点 + 全角形式」之外字符的占比，超过 `MOJIBAKE_MAX_RATIO=0.15` 判定该页文本层不可信，**强制走 OCR**，与「文本层过少」的长度规则互为补充；
- 乱码文本层必须被 OCR 结果**整体替换**，绝不拼接进索引——拼进去等于主动注入噪声；
- OCR 不可用/失败时乱码按原样保留 + 明确 warning（宁可透明也不静默）。

用白名单而不是黑名单的原因：乱码会散落在任意 Unicode 区块，黑名单枚不全；正常中文语料的主体字符集是封闭的，`·`（U+00B7）这类少量合法字符不会把占比推过 15%。

**遗留**：白名单对非中英文语料（越南文、阿拉伯文等）会把合法字符误判为异常，遇到这类语料需扩充 `_EXPECTED_CHAR_RANGES` 或调阈值；修复后**必须重入库**，且 `doc_id` 是内容指纹——重新入库的新文本 doc_id 不同，旧乱码 chunk 不会被整篇替换，需要 `reset` 后重建（见下）。

### 5.20 推理模型思维链吃光 max_tokens：空 content 被误判成「模型拒答」

**现象**：`ask -k mydocs -q "xxx的项目经历"`——检索完全正常（4 chunks 全召回、`gate_score 0.39` 过阈值、`llm_called: true`、耗时 17s），却返回拒答文案，调试信息里 `reason: "model_refused"`。而库内容明确包含"姓名：xxx"和两段项目经历。

**原因**：`.env` 配置的 `LLM_DEEPSEEK=deepseek-v4-pro` 是**推理模型**：思维链（`reasoning_content`）与正文（`content`）共享同一个 `max_tokens` 预算。上下文复杂/OCR 噪声多时，模型会思考很久——直接调 API 复现：`finish_reason: length`、`reasoning_tokens: 1199/1199`、`content_len: 0`，**1200 个 token 全被思考消耗，正文一个字没生成就被截断**。随后 `generator.py` 的 `text or NO_EVIDENCE_ANSWER` 把空文本替换成拒答模板，模板文案又命中 `_REFUSAL_MARKERS`（"知识库中没有"），被误标为 `model_refused`。同一个小上下文的简单问题则正常（reasoning 仅 92 tokens），所以问题只在"上下文足够复杂时"间歇性出现，极具迷惑性。

**解决**：两层修复。

① **关掉思维链（治本）**：`ChatClient` 新增 `thinking` 字段（`"disabled"`/`"enabled"`/`""` 不传），经 `extra_body={"thinking": {"type": ...}}` 注入——这是 DeepSeek 原生参数（422 报错信息暴露了服务端的 `ThinkingOption` 结构，探测确认 `chat_template_kwargs`/`enable_thinking` 会被静默忽略，只有 `thinking` 对象和 `reasoning_effort` 真正生效）。配置链：`.env` 的 `LLM_THINKING`（默认 `disabled`）→ `Settings.llm_thinking` → `RagConfig.llm_thinking` → `ChatClient.thinking`。RAG 问答是「依据检索结果抽取摘要」任务，不需要长链推理，默认关闭；查询改写与 LLM 重排复用同一 client，全链路生效。关闭后实测：一次调用直接生成 711 字完整回答，`reasoning_len=0`，耗时 17s→5.7s。

② **截断重试（兜底保险）**：`complete()` 首次响应 `content` 为空且 `finish_reason == "length"` 时，放大到 `max(4096, max_tokens*4)` 重试一次（带 warning 日志）；`finish_reason == "stop"` 的空回复不重试。thinking=disabled 时正常走不到这里，但防网关忽略参数、用户改回 enabled、或换模型的情况。

**遗留**：`max_tokens=1200` 对推理模型整体偏小——若日后把 `LLM_THINKING` 改回 `enabled`，复杂问题仍可能触发兜底重试（2 倍时延与 token 消耗）；长期应把生成预算做成独立配置项。

### 5.21 OCR 简历类文档 heading 全空：裸标题检测盲区 + 向量路未用 heading

**现象**：`sunzijie_resume.pdf`（OCR 文本层）入库后，`chunks.jsonl` 里所有 chunk 的 `heading` 均为空串。同时 BM25 侧早已实现「标题参与索引」（`bm25.py` 把 `chunk.heading` 拼进 tokenize 输入），但向量侧入库只编码 `chunk.text`——即便 heading 有值，向量路也拿不到任何增益，heading 沦为纯展示字段。

**原因**：`_split_headings` 只认两种标题形态——Markdown `#` 标题和「第X章 / 一、 / 1.1」式编号标题。OCR 出来的简历两个都匹配不上：

1. `基本信息` / `教育经历` / `项目经历` / `专业技能` 是**无编号裸短行**，正则直接不命中；
2. 更糟的是 `项目经历` 粘在上一节句尾（`…后训练范式 。项目经历`），根本不在独立行上；
3. OCR 把项目符号 `·` 识别成 `一`，`、 深度研搜平台` 这类行形态完全像正文。

机制本身没坏——对 Markdown / 研报（`# 标题`、`第X章`）heading 一直正常填充，这是「规则检测对无编号裸标题文档的盲区」。

**解决**：两处配套修复。

① **裸标题检测（chunking.py）**：新增 `_BARE_HEADING_WORDS` 词表（基本信息/教育经历/项目经历/专业技能/总结等 28 词）+ 结构双条件（整行 ≤12 字、不含句读标点）才判为标题，按二级挂靠（保留既有一级标题路径）。**不用纯长度启发式**是关键：OCR 文本里「山东济南」「中国香港」这类正文短行与标题形态几乎无法区分，词表 + 结构双条件才能把误判压住。另加 `_split_glued_heading` 剥离行尾粘连标题（标题前一个字符必须是句末标点，防「对全文进行总结」被误剥），正文留在上一节、标题开启新节。

② **heading 入向量（pipeline.py）**：新增 `_embed_input()`，向量编码输入变为 `f"{heading}\n{text}"`（heading 为空则原文），`ingest` 与 `add_texts` 两处入库统一走它，与 BM25 的「标题参与索引」策略对齐。**持久化的 `chunk.text` 不变**——展示/引用仍是干净正文。

**验证**（mydocs 真实简历，重建库后同一查询）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| heading | 全部空串 | 基本信息/教育经历/专业技能/项目经历 全命中（含粘连的"项目经历"） |
| gate_score（向量余弦，判定用） | 0.39 | **0.6192** |
| 引用显示 | `sunzijie_resume.pdf#3` | `sunzijie_resume.pdf#3 项目经历` |
| 拒答余量（阈值 0.35） | 0.04，极易误拒 | 0.27，余量翻近 7 倍 |

新增回归锁 6 个：裸标题识别、正文短行（山东济南）不误判、粘连标题剥离、剥离需句末标点前置、裸标题挂靠既有 H1、向量编码输入含 heading 前缀且 chunk.text 保持原文。

**遗留**：① 词表是封闭集合，未覆盖的裸标题（如「研究方向」「论文发表」）仍检测不到，遇到再补词；② OCR 错字（`Ski11s`/`孰悉`）对检索的伤害比 heading 更直接，属 OCR 质量问题，需换更好的 OCR 模型或做字符规整后处理；③ 旧库不重新入库不会享受 heading 增益（向量已按纯正文编码），且 `doc_id` 是内容指纹——文本没变时重新入库会整篇替换、自动生效。

## 六、未解决的问题（下一版候选）

按优先级排序：

1. **权限与多租户隔离**：知识库目前没有按用户/部门的访问控制，元数据已具备（frontmatter 抽取 + 过滤），但缺 ACL 与鉴权绑定。
2. **ANN 索引**：十万级片段以上必须引入 HNSW / IVF，或做「BM25 粗筛 + 向量精排」的分级检索。
3. **真实 BGE 语义向量验证**：当前所有指标仍基于 hash 兜底向量（无真正语义）；装上 `sentence-transformers` 换 local 后端后需**重新入库 + 重新标定 `RAG_MIN_SCORE`**。
4. **增量索引**：BM25 目前全量重建，大库入库会变慢。
5. **上下文压缩**：送入大模型的片段是原文，长片段会浪费 token，可以做句子级抽取式压缩。
6. **表格结构化检索**：现在表格被当普通文本，数值问答（求和、比较、筛选）不可靠，应走 SQL / 表格专用检索。
7. **生成质量评测落地**：RAGAS 方案已就绪（脚本 + 文档），但本机装不上依赖、judge 需付费，尚未跑过一次真实 RAGAS 评测。
8. **缓存增强**：无 TTL / 容量上限 / LRU / 跨进程锁（见 `rag-enterprise-features.md` §4.5）。

已从上一版"未解决"清单移除（本轮已实现）：扫描件 OCR（→ 方案 A，零依赖）、查询改写与多跳（→ 本地 + 大模型改写 + 低分重试）、生成质量评测（→ RAGAS 方案 + 离线替代）。

> **必须诚实说明这份指标的三点局限**：
>
> 1. **语料和评测集是我自己造的**，查询用词与原文高度重合，关键词路几乎必中。它证明「链路是通的、引用是对的、拒答是准的」，**不能证明语义检索质量好**——真实验收必须用业务语料和真实用户问法。
> 2. **重排没有体现出增量**（开/关指标相同）。原因是这份语料的查询太容易，候选里正确答案本来就在第 1 位，重排没有提升空间。要检验重排价值，需要「语义相近但用词不同」的查询和更大的候选池。
